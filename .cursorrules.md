# Plan Genie — Project Brief

## What this is
A web tool for event organizers. You lay out a room, add a schedule, and the
plan plays forward in time. When the layout and the schedule conflict, the tool
flags it — before the event happens.

**Tagline:** Plan your event before you run it.

## The problem (read this before making product decisions)
An organizer plans a 180-person community iftar in a rented hall. She has a
floor plan PDF and a run-of-show in a Google Doc. On paper it works. At 6:40pm
the talk ends, 180 people stand up at once, and the buffet line — one line,
starting eight feet from the main entrance — backs up across the only path to
the prayer area. Two volunteers are trying to fold tables in the middle of the
crowd because nobody told them it had to happen *before* the talk ended.

She had the layout. She had the schedule. She never had them together, so the
conflict was invisible until it was live.

## Who it's for
Someone running a 100–300 person community, campus, or mosque event with
volunteers and a rented hall. Not a professional wedding planner, not a
convention center. They cannot afford Cvent and have needs (prayer timing,
food service, multi-use of one room) that generic tools ignore.

## Core value — do not lose sight of this
The plan reveals its own failure before the event. The visual floor plan and
the time scrubbing are the *mechanism*. The value is the moment a conflict
lights up and the organizer moves the buffet six feet.

The signature interaction: **the warning clears while the user's hand is still
on the object they're dragging.** Build this first. Make it smooth. If only one
thing works, make it this.

## MVP scope

### In
- One room. Fixed rectangle. Top-down 2D view. **No 3D.**
- Placeable objects: round table, rectangular table, stage, buffet station,
  entrance/exit door, and a labeled zone rectangle (e.g. "prayer area", "queue").
- Drag to place, drag to move. That is the whole editor.
- A timeline of 3–5 blocks (e.g. Talk 6:00–6:35, Dinner 6:35–7:00,
  Prayer 7:00–7:20). Each block owns a layout state: objects can have a
  different position, or be marked "removed", per block.
- Scrub or play to move objects between states.
- Three conflict rules (see below), each firing a highlight plus a plain-English
  message.
- A read-only share link: same layout, mobile-friendly, timeline scrubber,
  nothing editable. No accounts, no login, no permissions, no realtime sync.

### Out — do not build these
- 3D rendering
- Crowd physics / pathfinding / agent simulation
- Venue import, floor plan PDF parsing, asset libraries
- Accounts, auth, database, multi-room, collaborative editing
- Anything that takes more than an hour and isn't on the demo path

## Conflict rules
All three are dumb, transparent, and rule-based. No simulation.

1. **Zone overlap** — two zones occupy overlapping space in the same time block.
2. **Capacity** — a zone's assigned headcount exceeds the capacity the user typed
   for it.
3. **Blocked path** — a straight line from a door to a zone passes through
   furniture or another zone.

Every message must name the cause in plain words and reference the user's own
numbers, e.g. "Flagged because you set capacity to 40 and scheduled 60."
Never invent clearance figures or throughput rates — the user sets them.

## Plan Genie (the assistant)
A small in-app suggestion row, not a mascot. When a conflict fires, it proposes
a concrete fix ("Move the buffet to the right wall to clear the path to the
prayer area") with an Apply button. Older, bearded, calm avatar. Keep it
restrained — the product must read as software, not a game.

## Build order
Stop wherever time runs out; every stopping point after step 3 still demos.

1. Room canvas + object placement and dragging
2. Timeline with per-block object positions
3. Zone overlap rule + warning UI  ← demo is viable from here
4. Blocked path rule
5. Capacity rule
6. Read-only share link (`/view/:id`), mobile layout
7. Volunteer setup view (`?role=setup` — highlights only objects that move,
   dims the rest)

## Demo script (90 seconds — protect this path)
1. Load the pre-built iftar layout.
2. Scrub to 6:00 — clean, no warnings.
3. Scrub to 6:40 — buffet queue and prayer zone flare red, warning text appears.
4. Drag the buffet six feet left. Warning clears live, mid-drag.
5. Open the same link on a phone: "this is what the volunteer sees when they
   walk in."

## Stack
- React + Vite, TypeScript
- Plain CSS or Tailwind — no component library
- All state in memory + URL/localStorage. No backend unless step 6 demands it.
- Drag: pointer events on absolutely-positioned divs, or react-dnd if needed.
  Do not reach for a canvas/WebGL library.

## Design tokens (from the approved landing page)
```
--bg:      #FFF7EC   warm cream background
--ink:     #33215C   deep purple text
--ink-70:  #6A5A88   secondary text
--ink-40:  #A79BBD   muted / labels
--grape:   #6C3FD1   brand, solid objects, primary button
--grape-dk:#5A2FBA   button shadow
--teal:    #17A79E   clear paths, doors, "ok" state
--amber:   #FFB23C   planned zones, highlight
--coral:   #E5483A   conflicts only
--card:    #FFFFFF
--rule:    rgba(51,33,92,.13)
```
Fonts: Fredoka (headings, buttons), Nunito (body). Rounded, friendly, but the
app UI itself stays precise — thin strokes, real dimension labels, a scale bar,
a proper time ruler with clock labels. Red is used for exactly one thing:
a conflict.

## Working agreement
- Commit after every working change. Git is the undo button.
- Once the demo path works, don't refactor through it. Build around it.
- Keep the conflict-detection logic in one file, clearly named.
- Ask before adding a dependency.
